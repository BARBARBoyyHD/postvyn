## 1. Executive Summary

Postvyn is a multi-profile content publishing workspace. One account holds several brands
("profiles"); each brand holds several channels (Instagram, Threads, YouTube, TikTok); each channel
holds a queue of posts moving through a documented status flow. The operator switches profile,
sees everything waiting, and ships it — several posts at once, on a schedule, with the platform
rules enforced before anything is sent.

Today this exists as a vault-shaped prototype: `brands/<brand>/social/<platform>/queue/<id>/`
plus a local dashboard. It works, but it is single-user, tied to one machine, and bend to a
folder layout rather than a product. Postvyn is the version that can be handed to someone
else — and eventually sold.

## 2. Problem & Opportunity

### The problem

| # | Problem | Today's workaround | Cost |
|---|---------|-------------------|------|
| 1 | One person runs several brands, each with its own voice, accent, handle and channel set | mentally track which handle/colour applies | wrong-brand posts, inconsistent identity |
| 2 | Every platform has different limits (chars, hashtags, aspect, media size) | read `specs.md` by eye before posting | rejected posts, truncated captions |
| 3 | Publishing is per-platform, manual, repetitive | open each app, paste, upload | hours/week, drift, missed slots |
| 4 | Platform APIs each need a different auth/upload flow | don't automate; post by hand | no scheduling, no batching |
| 5 | Autonomous poster in the tools layer is *forbidden* on TikTok | in-app scheduler | one manual step stays |

### Why now

The queue model, spec enforcement and direct publishers already exist and are proven against
real content. What is missing is a product shell: persistence beyond a folder tree, a real
profile switcher, scheduling that survives a closed laptop, and a path to multiple users.

### Opportunity

- **Own use (v0.1–v1.0):** one operator, 2+ brands, 4 channels, $0 running cost.
- **SaaS (v2+):** agencies and solo operators running multiple client brands — the same shape,
  with tenant isolation and billing.

## 5. Scope

### In scope (v1.0)

- Email/password or OAuth login, single operator + invited editors
- Workspace → Brand (profile) → Channel → Post, with per-brand voice and theme
- Queue board per profile with status columns and bulk actions
- Per-platform caption variants under one content item
- Spec validation (chars, hashtag counts, media type/size/aspect) before publish
- Approval gate with audit trail (who approved, when, what was sent)
- Scheduling executed server-side (not on the operator's machine)
- Direct publishers: Instagram, Threads, YouTube (video uploads: regular VOD + Shorts)
- TikTok: manual upload pack (deliberately not automated)
- Media library with public URLs for platforms that fetch media
- Activity log per post

> **Platform lineup amended 2026-11-17:** X is removed from the product (decision: pay-per-use per
> post — $0.015, $0.20 with a link — is not worth metering); YouTube takes its slot with video
> uploads only (VOD + Shorts), metered by API quota. The principle is unchanged: the scarce resource
> is shown before it is spent. See §8 for the constraints either side of the swap.

### Out of scope (v1.0)

- Analytics/insights ingestion — v2
- Comment/DM management — v2
- AI copy generation — deliberately out (voice quality is the product)
- Billing — v2
- TikTok automation — permanently out (see R-1)
- Facebook Pages, LinkedIn, Pinterest — adapters are pluggable; not v1
- X (Twitter) — **removed from the product 2026-11-17**; no adapter, no cost model, no connect path
  ships (the pay-per-use economics lost the argument)
- Mobile app — responsive web only
- Team-level permissions beyond editor/viewer

## 6. Core Concepts & Information Architecture

```
Workspace (tenant boundary, billing unit)
└── Brand / "profile"            voice, accent, handle, links
    └── Channel                  one platform account (ig / threads / youtube / tiktok)
        └── Post                 a content item: status, pillar, assets, schedule
            └── Variant          per-platform caption + hashtags + media selection
```

| Concept | Rule |
|---|---|
| **Brand** is the unit the operator switches on | voice + colour + channel set travel together |
| **Post** is the unit of approval | one post can have several variants; approval is per variant |
| **Variant** is the unit of publishing | one variant → one channel → one platform call |
| Status flow is fixed | `idea → researched → drafting → review → approved → scheduled → published` |
| Forward-only | moving backwards requires an explicit reason recorded in the log |

## 7. Functional Requirements

### FR-01: Authentication & Workspace

```
/login          email + password, or GitHub OAuth
/onboarding     create workspace → add first brand
```

| Field | Required | Default | Description |
|---|---|---|---|
| email | yes | — | unique per user |
| workspace | yes | auto | created on first login |
| role | yes | owner | `owner` \| `editor` \| `viewer` |

**AC:** an editor can create and edit posts but receives `403` on any publish endpoint.

### FR-02: Brand (Profile) Management

| Field | Required | Default | Description |
|---|---|---|---|
| name | yes | — | display name, e.g. "Zavron" |
| handle | yes | — | `@zavron.dev` |
| voice | no | — | written voice note, injected into composer hints |
| accent / bg0 / bg1 | no | theme presets | drives UI theming and asset generation tokens |
| links / accounts | no | — | website, per-platform profile URLs |

**AC:** switching brand re-themes the UI and filters every list; no query returns rows from
another brand without an explicit cross-brand view.

### FR-03: Queue Board

- Columns by status, counts per column, filter by channel and pillar
- Card shows: channel, format, caption preview, hashtags, spec verdict, schedule, last action
- Multi-select → bulk `approve`, bulk `schedule`, bulk `move to review`

**AC:** bulk approve of 10 posts completes in ≤ 2 s and writes 10 audit entries.

### FR-04: Composer & Per-Platform Variants

- One content item, N variants (one per target channel)
- Caption character counter **counts the way the platform counts** — each platform's rule lives in
  the spec engine (YouTube counts UTF-8 bytes)
- Hashtag bucket per platform (IG: first comment; Threads/YouTube: in the caption)
- Media picker from the library; per-variant media order for carousels
- Draft autosave every 5 s

**AC:** the counter never disagrees with the platform's own limit check.

### FR-05: Spec Validation Engine

Single source of truth per platform: sizes, caption max, hashtag range, media caps.
Runs on every edit and again immediately before publish.

| Rule kind | Behaviour |
|---|---|
| hard error (over caption limit, wrong media type, missing asset) | blocks publish, names the field |
| warning (hashtag count outside range, unexpected aspect) | allows publish, visible in review |
| override | permitted, requires a typed reason, recorded in the log |

### FR-06: Approval Gate

- `review → approved` requires an authenticated human action
- Approval captures: user, timestamp, variant hash (what exactly was approved)
- If the variant changes after approval, approval is invalidated and the post returns to `review`

**AC:** a post edited post-approval cannot publish without re-approval.

### FR-07: Scheduling & Execution

- Operator sets a slot; server-side scheduler claims due posts
- No dependency on the operator's machine being awake
- Idempotent: a claimed post cannot be published twice (lease + unique constraint)
- Retry policy: exponential backoff, max 3 attempts, then `failed` with the platform error

### FR-08: Publisher Adapters

| Platform | Flow | Notes |
|---|---|---|
| Instagram | container → poll `status_code` → `media_publish` | media must be publicly fetchable |
| Threads | container → poll `status` → `threads_publish` | 250 posts / 24 h |
| YouTube | resumable upload (VOD + Shorts) → `videos.list` read-back | quota shown pre-upload; default 100 uploads/day |
| TikTok | **none** — generates an upload pack | see R-1 |

**AC:** every publish is read back from the platform and stored before status becomes
`published`. A 200 response alone is never treated as success.

### FR-09: Manual Pack (TikTok)

- Generates caption + hashtag block + asset link + upload checklist
- Lives with the post so the operator can complete it in-app and mark it done

### FR-10: Activity Log

Append-only per post: created, edited, approved, scheduled, publish attempted, publish
succeeded/failed, manual completion. Filterable per brand.

### FR-11: Media Library (v1)

- Upload once, hashed, deduplicated, served from object storage
- Review artifacts (contact sheets, thumbnails) flagged as non-postable and excluded
- Soft delete; purge job for orphans

## 8. Platform Constraints (product-shaping, not implementation detail)

| Platform | Direct publishing | Gate |
|---|---|---|
| Instagram | yes | account must be Business/Creator; Standard Access = no App Review while the app serves only accounts you own |
| Threads | yes | account added as a tester on your app; no review needed |
| YouTube | yes | Google OAuth2 (client id/secret + refresh token per channel, entered in the app); consent screen must be **In production** (Testing = 7-day tokens); default quota 100 uploads/day + 10,000 units — shown before upload |
| TikTok | **no** | guidelines reject "a utility tool to help upload contents to the account(s) you or your team manages"; unaudited clients post `SELF_ONLY` |

> **Amended 2026-11-17 (platform lineup):** X is removed from the product — its constraint was
> economics: no free tier since Feb 2026, $0.015/post, $0.20 with a link, prepaid credits. The
> decision is to drop it rather than meter it. YouTube takes its slot (video uploads: VOD + Shorts),
> and its scarce resource is API quota rather than money. The principle survives the swap: **the
> scarce resource is shown before it is spent.**

**SaaS consequence (critical):** the moment Postvyn serves accounts it does not own, the
Meta side flips from Standard Access to **Advanced Access + App Review + Business Verification**,
and every tenant either connects through the operator's audited app or brings their own app
credentials. TikTok cannot be offered as an automated channel at all. This is the largest
unknown in the SaaS path and is tracked as OQ-1.

## 9. Non-Functional Requirements

| # | Requirement | Target |
|---|---|---|
| NFR-01 | Cost for a solo operator | ≤ $3/mo (free tiers; YouTube is metered by quota, not money) |
| NFR-02 | Cold page load (queue board, 200 posts) | ≤ 1.5 s p75 |
| NFR-03 | Publish job reliability | ≥ 99% success excluding platform outages; never double-post |
| NFR-04 | Tenant isolation | enforced by a single scoped repository (D1 has no RLS) + a lint rule + cross-workspace tests — a recorded downgrade from the original RLS target |
| NFR-05 | Secrets | platform tokens encrypted at rest, per channel, rotated on re-connect |
| NFR-06 | Portability | deliberately single-vendor (Cloudflare) for MVP; export path `wrangler d1 export` → SQLite → Postgres ≈ 2 days, recorded rather than assumed |
| NFR-07 | Operability | one deploy, one database, one log stream; a solo dev can run it a year without help |
| NFR-08 | Accessibility | WCAG 2.2 AA on the board and composer |
| NFR-09 | Auditability | every publish traceable to a user, a variant version and a platform response |

## 10. Technical Decision — Next.js full-stack vs Next.js + Go

### Options

| | **A. Next.js full-stack** | **B. Next.js UI + Go API/worker** |
|---|---|---|
| Languages | TypeScript only | TypeScript + Go |
| Deploys | 1 (one Worker) | 2 (web + service), plus a queue |
| Auth | one session layer (hand-rolled, signed cookie) | session in Next, service tokens in Go — two layers to keep honest |
| Types | shared end-to-end | duplicated or generated from OpenAPI |
| Long-running work (YouTube resumable upload, IG/Threads polling) | needs a background worker **anyway** | natural fit for a service |
| Cost at this scale | $0–5/mo | + a host for the service |
| Solo-dev maintenance | one repo, one dependency tree | two repos/trees, drift between them |
| Performance ceiling | far above 15 posts/week | far above 15 posts/week |
| Hiring/handover | one skill set | two |

### Decision

**ADR-001 — Build on Next.js-shaped code (App Router, Route Handlers, server actions) deployed to
Cloudflare Workers via vinext, with D1 for data and S3-compatible object storage. No separate Go
service in v1.**

*(Amended 2026-11-15: the original decision named Postgres/Neon. Neon's scale-to-zero made the first
request after idle a unwelcome wait, so the host changed to D1 — see ITA ADR-013…018. The
"one runtime, no separate service" half of this decision is unchanged and still binding.)*

Reasoning: at the product's real load (tens of posts per week) language-level performance is
irrelevant, while two runtimes double the operational surface — the exact cost the target user
cannot absorb. The one genuine argument for a separate service is long-running I/O, and that is
solved by a **job table + worker loop**, not by a second language.

### The seam that keeps the Go option alive

- All platform I/O sits behind a `Publisher` port (`publish(variant) → PublishResult`, `verify(id)`)
- Jobs are rows (`jobs`: `id, kind, payload, state, attempts, run_after, lease_until`)
- The worker is a plain Node process consuming that table — it can be replaced by a Go binary
  without touching the web app, because the contract is the database, not HTTP

### Revisit trigger (write it down, or the argument repeats forever)

Adopt Go only if **one** of these becomes true:

1. sustained volume > 100 publishes/day, or > 20 concurrent long uploads; or
2. media transcoding (ffmpeg) becomes a first-class feature; or
3. self-hosting on a VPS where a single static binary materially simplifies ops; or
4. the web app's Node worker becomes a measured reliability bottleneck (not a suspected one).

### Supporting choices

| Area | Choice | Why |
|---|---|---|
| Runtime | Cloudflare Workers via **vinext** (Next.js API on Vite) | no cold start, no server to patch; Cloudflare's default Next-on-Workers path since Sept 2026 |
| DB | **Cloudflare D1** (SQLite) + Drizzle | no cold start, no idle billing; text-only rows are well inside its limits |
| Tenant isolation | scoped repository + lint rule + cross-workspace tests | RLS does not exist in D1 — a recorded downgrade, not a hidden one |
| Media | Cloudflare R2 (S3 API) | free tier, zero egress, public bucket URLs platforms can fetch |
| Auth | hand-rolled sessions (signed cookie + D1 table), scrypt | Auth.js on a beta runtime is risk without payoff for one user |
| Jobs | `jobs` table + cron trigger (1-min tick) | no always-on process on Workers; survives restarts |
| Hosting | Cloudflare (Workers + D1 + R2) | one vendor, $0–5/mo, nothing to patch |
| Observability | Workers Logs + `activity_log` table | no third-party dependency at this size |

## 11. Data Model (sketch)

```
users(id, email, password_hash, created_at)
workspaces(id, name, plan, created_at)
memberships(user_id, workspace_id, role)            -- scoping hinge (D1 has no RLS)
sessions(id, user_id, expires_at)                   -- signed-cookie sessions
brands(id, workspace_id, name, handle, voice, colors json)
channels(id, brand_id, platform, account_ref, label, status)   -- many per platform per brand
channel_credentials(channel_id, ciphertext, iv, key_version)   -- AES-256-GCM, never hashed
posts(id, brand_id, title, format, status, pillar, schedule_at, created_by)
variants(id, post_id, channel_id, caption, hashtags json, media_ids json, spec_state)
media(id, workspace_id, hash, path, mime, bytes, width, height, postable bool)
approvals(id, variant_id, variant_hash, user_id, approved_at)
jobs(id, kind, payload jsonb, state, attempts, run_after, lease_until)
publish_results(id, variant_id, platform_post_id, url, raw jsonb, created_at)
activity_log(id, workspace_id, post_id, actor_id, action, detail jsonb, created_at)
```

Invariant: `approvals.variant_hash` must equal the current variant hash at publish time.

## 12. Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R-1 | TikTok automation is ToS-prohibited | certain | medium (one channel manual) | manual pack; never ship an uploader |
| R-2 | Meta tokens expire / app re-review on SaaS upgrade | high | high | token refresh job; document the Advanced Access path before promising SaaS |
| R-3 | Serving other people's accounts requires App Review + Business Verification | high (on SaaS) | high | treat as a v2 gate, not a v1 detail; OQ-1 |
| R-4 | YouTube quota model changes or the daily budget runs out | medium | medium | quota shown pre-upload; constants cited with a read date; the Console quota page wins disputes; a quota increase needs Google's audit |
| R-5 | Platform API breakage (field/aspect/limit changes) | medium | medium | adapters isolated; specs mirrored in code and re-checked against `social/*/specs.md` |
| R-6 | Scope creep into a full CMS | high | high | §5 out-of-scope list is the contract |
| R-7 | Double-publishing under retry | medium | high (public) | lease + unique constraint on `variant_id` publish |
| R-8 | Migration of the existing folder queue loses history | low | medium | importer writes each folder as post+variant, verbatim |

## 15. Glossary

| Term | Meaning |
|---|---|
| **Workspace** | tenant boundary; billing and isolation unit |
| **Brand / profile** | a person or company with its own voice, colours and channels |
| **Channel** | one connected platform account under a brand |
| **Post** | a content item moving through the status flow |
| **Variant** | the per-platform rendering of a post (caption, hashtags, media) |

| **Approval hash** | fingerprint of a variant at approval time; invalidates on edit |
| **Manual pack** | generated upload sheet for platforms with no automatable path |
