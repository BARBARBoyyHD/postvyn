## Context

The repository holds complete product documentation and a freshly scaffolded Next 16 app, but no
data layer, no Workers build path and no CI. The decisive constraint is that D1 is SQLite: no
row-level security, no `SKIP LOCKED`, no interactive transactions across awaits, and a 50-query
budget per invocation on the free plan. Everything in this design follows from those four facts plus
ADR-013…020 in `docs/003-ITA.md`.

Second constraint: vinext is 1.0 but young. The design keeps as much logic as possible out of
framework-shaped code, so a vinext regression cannot reach the domain.

## Goals / Non-Goals

**Goals:**

- A project that installs, builds, type checks and lints with one command each, on a fresh clone,
  with no secrets.
- The full data model as reviewed SQL migrations, applied from empty in one command.
- One chokepoint for tenancy that a compiler and a lint rule both defend.
- An isolation test that runs in the real Workers runtime and fails when the boundary breaks.
- A deployable Worker whose bindings are declared and whose first deploy is a smoke test.

**Non-Goals:**

- No authentication, no session, no user (M1).
- No board, no importer, no composer, no approvals, no publishing (M2 onward).
- No R2 uploads; the binding is declared but unused (M6).
- No cron logic; the trigger exists but the handler is a no-op (M4).
- No test suite beyond the isolation proof and the handful of unit tests that prove the repository
  contract. The project deliberately has no broad test scaffolding yet — stories are still moving.

## Decisions

**1. Run `vinext init` now, before the schema lands.**
The dependency tree is two packages thick today and will be twelve after M1. Converting now means the
schema and the tenancy layer are written against the runtime they will actually ship on. Alternative
considered: stay on plain Next and convert later — rejected because plain Next cannot hold a D1
binding at all, which would force a throwaway database layer.

**2. `src/db` owns the binding; the repository is the only public surface.**
The module exports repository functions that take `WorkspaceContext`, and does not export the Drizzle
client or the raw binding. Enforcement is layered: (a) `no-restricted-imports` lint rule on
`@/db/client`, (b) the isolation test, (c) review. Alternative: a `drizzle(...)` call per route
handler — rejected as exactly the failure mode the missing RLS cannot catch.

**3. Isolation test runs in `vitest-pool-workers` against real `workerd`.**
A mocked D1 would prove nothing about SQL, indexes or constraints. The cost is slower tests and a
second wrangler config; the benefit is that the one guarantee we lost (database-enforced tenancy) is
the one thing under real test. Alternative: node-side SQLite (better-sqlite3) — rejected because it
would not catch a D1-specific behaviour change.

**4. Our tables in M0, identity tables in M1.**
Better Auth's tables are generated by its CLI from the auth config, which does not exist until M1.
Splitting them keeps each migration reviewable and avoids a hand-written guess at the auth schema.
Consequence: migration `0001` is ours alone.

**5. Timestamps are integer milliseconds, ids are text UUIDs.**
SQLite has no native uuid or timestamptz. Millisecond integers compare correctly, sort correctly and
survive the JSON envelope without lossy formatting. Alternative: ISO text — rejected because string
comparison of timestamps with mixed offsets is a bug waiting for the first timezone change.

**6. Jobs and publish results are defined now, used later.**
The two unique indexes (`one_publish_per_variant`, `one_account_per_platform`) are the schema's
load-bearing safety features and belong in the first migration, even though nothing writes to them
until M4/M5. Adding a unique index to a table that already holds duplicates is a painful migration;
adding it while the table is empty is free.

**7. Typecheck is `next typegen && tsc --noEmit`.**
Next 16 supplies `LayoutProps`/`PageProps` as generated types. Baking typegen into the script means a
clean clone and CI behave like a warm local tree, instead of only the warm tree passing.

**8. The app is a standalone project, not a workspace member.**
`apps/frontend` owns its `pnpm-lock.yaml`, `packageManager` pin and `onlyBuiltDependencies`; the
repository root holds documents and `openspec/` only. Reasons: the Cloudflare Worker's build root is
`apps/frontend`, so the lockfile now sits in the directory the build actually runs from (no walking
up, no watch-path config to keep in sync), and there is exactly one deployable, so a workspace buys
nothing yet. Trade-off, stated plainly: the layering boundary is no longer enforced by install-time
strictness — with one package there is nothing to be strict *between* — so it falls to the
`no-restricted-imports` rule plus review. Revisit if a second deployable appears (the publisher
worker is the likely trigger), at which point the workspace returns and `turbopack.root` comes back
with it.

## Risks / Trade-offs

- **`vinext init` may conflict with the turbopack CSS loader rule that Tailwind uses** → after init,
  verify styling still compiles; fall back to Tailwind's Vite plugin if the rule is ignored.
- **pnpm's strict linking can surface resolution errors that npm hid** → already observed with Better
  Auth peers. Treat as signal, not noise; override only with a recorded reason.
- **Isolation depends on discipline** → mitigated by lint rule + test, but a dynamic import can still
  bypass lint. The test seeds two workspaces precisely so a deliberate bypass fails loudly.
- **CI migration checks can collide across parallel branches** → migrations are numbered and reviewed;
  the pipeline applies them to a throwaway database, so a conflict fails the branch that caused it.
- **Free-plan query budget (50 per invocation)** → the repository's list functions are batch-shaped
  from the start; the board will not be able to introduce N+1 later without failing a budget test.
- **Workers CPU ceiling on the free plan** → not exercised in M0; if SSR exceeds it during M2, the
  documented response is Workers Paid ($5), not a redesign.

## Migration Plan

Greenfield: there is no existing data and no deployed surface, so there is nothing to migrate.

- **Apply:** land the change on a branch, run the gates, deploy to `*.workers.dev` only. No custom
  domain yet, so nothing is publicly addressable beyond the workers.dev host.
- **Rollback:** revert the commit; drop the local D1 state directory. Since the schema is created by
  migrations from empty, a rollback leaves no orphaned state anywhere real.
- **Forward:** M1 adds auth tables as `0002`, so the same pipeline proves the second migration.
