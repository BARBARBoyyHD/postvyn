## ADDED Requirements

### Requirement: Schema covers every documented entity

The database schema SHALL define the tables described in the architecture document for identity
boundaries, workspaces, memberships, brands, channels, channel credentials, posts, variants, media,
approvals, jobs, publish results, sessions and the activity log. Better Auth's identity tables are
mapped through its adapter rather than hand-written.

#### Scenario: All entities exist after migration

- **WHEN** migrations are applied to an empty database
- **THEN** every table named in the architecture document exists
- **AND** each table exposes the fields that document lists

#### Scenario: Identity tables belong to the auth library

- **WHEN** the schema is reviewed
- **THEN** the identity tables are generated by the auth library's tooling, not authored by hand
- **AND** no column of ours references an internal field of those tables

### Requirement: Migrations apply from empty with one command

Schema changes SHALL be expressed as plain SQL migration files applied through the platform's D1
migration command, and a fresh database MUST reach the current schema with a single documented
command.

#### Scenario: Empty database becomes current

- **WHEN** the local migration command runs against an empty local database
- **THEN** it completes without manual intervention
- **AND** a second run is a no-op

### Requirement: A variant can only be published successfully once

The schema SHALL enforce uniqueness of successful publish results per variant at the database level,
so a retry or a duplicate job cannot create a second live post.

#### Scenario: Duplicate publish result is rejected

- **WHEN** a second successful publish result is written for the same variant
- **THEN** the database rejects the write
- **AND** the first result remains intact

### Requirement: An account is unique per brand, platform and account reference

The schema SHALL prevent two channel rows describing the same account for the same brand and
platform, while still allowing many channels per platform per brand.

#### Scenario: Duplicate account is rejected

- **WHEN** a channel is created with the same brand, platform and account reference as an existing
  channel
- **THEN** the database rejects the insert

#### Scenario: A second distinct account is allowed

- **WHEN** a channel is created for the same brand and platform with a different account reference
- **THEN** the insert succeeds
- **AND** both channels remain queryable for that brand

### Requirement: Timestamps are stored in UTC at millisecond precision

All timestamps SHALL be stored as integer Unix milliseconds in UTC. A display timezone MAY be applied
when rendering, but MUST NOT be used for comparison or scheduling.

#### Scenario: Scheduling compares in UTC

- **WHEN** a job's due time is compared to the current time
- **THEN** the comparison uses absolute UTC instants
- **AND** the workspace timezone affects only what is shown to the operator
